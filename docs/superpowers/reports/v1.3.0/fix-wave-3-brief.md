## H1 [high] positive-pid fallback after group ESRCH can signal a recycled pid — plugins/codex/scripts/lib/process.mjs (~245-250, the G1 fallback) and terminateRecordedProcess
`terminateProcessTree` now does `kill(pid)` right after `kill(-pid)` raised ESRCH, without re-verifying ownership; for a recorded pid (no child handle) the process may have exited and been reused between the identity check and the second syscall.
Fix: move the fallback decision up one level. `terminateProcessTree` posix: on ESRCH from the group kill return `{ attempted: true, delivered: false, method: "process-group", groupGone: true }` (no positive-pid signal inside this primitive). `terminateRecordedProcess`: when the outcome has `groupGone`, re-verify ownership immediately (identity given → `getProcessIdentity(pid)` must still equal it; else posix command-line match must still hold); on success `killImpl(pid, "SIGTERM")` and report `delivered: true, method: "process"`; on mismatch/unavailable return `attempted: true, delivered: false, reason: "identity-mismatch"|"identity-unavailable"`. The fresh-broker child-handle path (G2) keeps its own `child.kill` fallback and is unaffected. Tests (tests/process.test.mjs): (a) identity stays matching → calls `[[-42,"SIGTERM"],[42,"SIGTERM"]]`, two identity reads; (b) identity changes between the reads → only the group call, no positive signal, `reason: "identity-mismatch"`; (c) legacy command-line path: line changes between reads → refused. Update the G1 unit tests accordingly.

## H2 [high] truncated command lines can reap a live legacy job — process.mjs `processCommandLine` (+ every consumer: reaper G3 rule, ownsBrokerProcess, workerCommandLine)
`ps -o command=` honours `COLUMNS` on Linux procps even when piped; an 80-column line can cut `codex-companion.mjs` off a long install path, and the G3 rule then reaps a live job.
Fix: linux → read `/proc/<pid>/cmdline` (NUL-separated → join with spaces; empty/unreadable → null) via `readFileSyncImpl`; darwin/other posix → `ps -ww -o command= -p <pid>` with `env: { ...process.env, COLUMNS: "10000", LC_ALL: "C" }`, `shell: false`. Treat empty output as null (unknown). The reaper's G3 rule and `ownsBrokerProcess` must treat null as unknown (no action) — verify they do. Tests: linux branch with an injected `readFileSyncImpl` returning `node\0/very/long/path/codex-companion.mjs\0task-worker\0` → contains marker; darwin branch asserts `-ww` in args and `COLUMNS` in env; reaper test: `processCommandLineImpl` returning a long line that ends before the marker (simulated truncation) is NOT possible any more by construction — instead assert the reaper leaves the job alone when the impl returns null.

## H3 [high] SessionEnd removes foreground job records it never stopped — plugins/codex/scripts/session-lifecycle-hook.mjs cleanupSessionJobs (~140-154)
The kill outcome is discarded and the filter removes every foreground job of the session; a refused/undelivered kill (identity mismatch/unavailable, win32) or a job skipped because the budget ran out loses its record and artifacts while the worker keeps running.
Fix: collect the outcome per job: remove the record only when the kill was delivered (`attempted && delivered`) OR the pid is provably dead (`isPidAlive === false`) OR the job has no pid; keep every other job (refused, undelivered, skipped for budget — `remainingMs() < MIN_STEP_MS` before the job was reached) in `state.jobs` untouched, log one stderr line per kept job (`[codex] SessionEnd left <id> running: <reason>`), and let `activeWorkspaceJobs` see them so the broker stays up. Tests (tests/broker-stale-pid.test.mjs or a hook test): (a) foreground running job whose stored `pidIdentity` mismatches the live pid → after SessionEnd the record is still present with status running, sidecar/request file intact, and the hook's stderr names it; (b) budget exhaustion: inject `CODEX_COMPANION_SESSION_END_BUDGET_MS` small with a slow `getProcessIdentity` (or several jobs) → unreached jobs are kept; (c) delivered kill still removes the record (existing behaviour).
