## G1 [high] cancel acknowledges termination when nothing was delivered — plugins/codex/scripts/lib/process.mjs `terminateProcessTree` posix branch (~236-256) and codex-companion.mjs handleCancel (~1331-1336)
Root cause: `killImpl(-pid, "SIGTERM")` raises ESRCH when the pid is NOT a process-group leader (a foreground worker, or any child spawned without `detached`), and the ESRCH branch returns `{attempted:true, delivered:false}` WITHOUT trying the pid itself, although the process is alive. `handleCancel` then treats `attempted` as success, writes `cancelled`, deletes the sidecar, and the surviving worker later overwrites it with `completed`.
Fix (both halves):
1. `terminateProcessTree` posix: on ESRCH from the group kill, fall back to `killImpl(pid, "SIGTERM")`; only when that also raises ESRCH return `delivered:false, method:"process"`. Unit test in tests/process.test.mjs: `killImpl` throws ESRCH for negative pids and records positive ones → `delivered:true, method:"process"`, calls `[[-4242,"SIGTERM"],[4242,"SIGTERM"]]`.
2. `handleCancel`: the pending branch triggers when `pid && (!kill.attempted || !kill.delivered) && isPidAlive(pid) === true` (undelivered = pending, same output/exit 1/JSON as the refused case; reason from `kill.reason` or `"not-delivered"`). Additionally protect an acknowledged cancellation from later worker writes: when cancel does write the terminal `cancelled` record, `runTrackedJob`'s terminal write must not overwrite a record whose stored status is already `cancelled` (check inside the same lock before writing; keep the worker's result in the log only). Test: real background worker (fake codex, `FAKE_CODEX_TURN_DELAY_MS`), cancel it (delivered), then wait for the worker exit → stored status stays `cancelled`.
Regression for the ESRCH case end-to-end is optional (hard to force a non-leader worker); the unit test + cancel branch test suffice.

## G2 [medium] fresh-broker cleanup leaves the app-server descendant alive — broker-lifecycle.mjs (~282-298)
`child.kill("SIGTERM")` signals only the broker; app-server-broker.mjs installs its cleanup handlers after awaiting initialization, so a broker stuck in connect dies without tearing down its app-server child.
Fix: in the verified branch (`child.exitCode === null && child.signalCode === null`, no await in between) use the process-group kill: `killProcess(child.pid)` (default `terminateProcessTree`, which does `kill(-pid)` — the child is detached, so it is its own group leader; its pid/pgid cannot be reused while our handle has not observed the exit). Keep the exited-child guard from A1 (no signal at all when exited). Drop the `child.kill` step or keep it only as the fallback when the group kill reports `delivered:false`. Update the fresh-broker tests: the never-listens test asserts the recording killer was called with `child.pid`; the exited-child test asserts it was not.

## G3 [medium] refused legacy cancellation cannot converge while a recycled pid lives — tracked-jobs.mjs reapDeadJobs (~394-405)
A running record without `pidIdentity` whose pid now belongs to an unrelated long-lived process is never reaped (reaper only acts on identity mismatch), so cancel stays pending forever and the thread stays "in use".
Fix: in `reapDeadJobs`, when `identity` is null and platform is posix, read `processCommandLine(pid, { timeoutMs: min(2000, remaining) })`; if it is a non-empty string that does NOT contain `codex-companion.mjs`, mark the job dead with `${DEAD_WORKER_MESSAGE} (worker pid ${pid} now belongs to an unrelated process)` — without signalling anything. Unreadable/null command line → leave the job alone. Inject via `options.processCommandLineImpl`. Test in tests/tracked-jobs.test.mjs: seed `running` job with `pid: process.pid`, no `pidIdentity`, `processCommandLineImpl: () => "/usr/sbin/unrelated-daemon"` → failed with that message; with impl returning a line containing `codex-companion.mjs` → still running; impl returning null → still running.
