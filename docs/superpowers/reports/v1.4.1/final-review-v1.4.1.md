### Strengths
- The kill script (`plugins/codex/scripts/lib/process.mjs:459-540`) does what spec §3.4 asks in one PowerShell run: root pinned via `GetProcessById` + `.Handle` before `StartTime` is read; children admitted only when the pinned start time equals the CIM `CreationDate` at exact `Int64` microseconds and is not earlier than the parent's (defeats stale `ParentProcessId` after PID reuse); exclusion decided only after the pin, by `(pid, start-time)` pair; children-first `Kill()` through pinned objects; survivors reported with the identity read from the still-pinned object before `Dispose()`; every branch inside one `try/finally`. No external program is started.
- The JS mapping (`process.mjs:551-599`) is genuinely fail-closed: exit code classifies, protocol refines, any contradiction is `unverified`; exit 0 with junk is not delivered; 241/242 with any stdout become `identity-unavailable`; 243 survivor rows must be unique valid pids. The 22-case table in `tests/process.test.mjs` pins all of it.
- Every `powershell.exe` launch in the repo — plugin, `scripts/check-leaks.mjs`, `tests/helpers.mjs cimTree` — goes through `runPowerShell`: validated `SystemRoot`, absolute path, clean environment (only `LOCALAPPDATA`/`PSModuleAnalysisCachePath` passed through, absolute-only), `System32` cwd, `-EncodedCommand`, `shell:false`. Both workflows no longer invoke `powershell` directly. The E2E at 324 plants `powershell.exe`/`.cmd` shims and a relative `PATH`, and the probe still answers `win32:`.
- Breaker scope is right after the Task 4 fix: probe timeouts, ENOENT, invalid root and 244 trip it; kill timeouts (`tripOnTimeout:false`) and 245 do not, so one slow target cannot blind the next kill. Tested both ways.
- Caller integration is coherent: `cancelDecision` keeps a job `running` on survivors/unverified even with a dead root; `cleanupSessionJobs` keeps unresolved trees and logs them; `teardownBrokerSession` keeps records only under `keepOnUnknown` from the hook; `ensureBrokerSession`'s stale replacement still replaces. Legacy records without identity are refused everywhere on win32; posix keeps the v1.4.0 reasons and JSON byte-for-byte (`renderCancelPending` test).
- The U+2028/U+2029 fix is minimal and correct: `stdout.setEncoding("utf8")` is already set (`app-server.mjs:261`) so the `"\n"`-only splitter cannot corrupt multi-byte sequences across chunks; the fake-codex test proves the frame arrives whole.
- SessionEnd budget arithmetic holds: every step is clamped by `remainingMs`; 1 job → 4 s kill + ≤ 4 s teardown; 2 jobs → 4 + 4 + teardown ≥ 750 ms; 3 jobs → 4 + 4 + 2 and the teardown gets whatever is left or `budget-exhausted`. Nothing runs unclamped except spawnSync overshoot, so the 15 s hook timeout is never approached.
- Windows E2E is the real thing (direct tree with `cimTree` names, brokered A with `appServerStarts` staying 1 and the same broker pid, tampered indexed+file identity, hung broker torn down by identity, planted launcher), with 90–120 s ceilings and relative waits per roadmap constraint 8.

### Issues

#### Critical (Must Fix)
None.

#### Important (Should Fix)
1. **`process.mjs:483` — the "no CommandLine" snapshot is a client-side projection, not a cheaper query.** `Get-CimInstance Win32_Process | Select-Object ProcessId, ParentProcessId, CreationDate` makes the provider compute every property, including the expensive `CommandLine` (one PEB read per process), before `Select-Object` drops it. Spec §3.4 rev. 12 and the ledger both describe this as the cheaper snapshot — that is a spec-level misconception the code copied. Why it matters: the SessionEnd kill step is 4 s with a 3.5 s script deadline and `Remaining` is checked only *after* the snapshot; on a desktop with a few hundred processes the snapshot can eat the budget and every SessionEnd ends `245 → identity-unavailable → kept` (fail-closed, but the worker is never killed and the user sees `kept=true` forever). I cannot measure this on this host; hosted runners (fewer processes) pass. Fix: `Get-CimInstance -ClassName Win32_Process -Property ProcessId,ParentProcessId,CreationDate` (provider-side projection), same for `cimTree` in `tests/helpers.mjs:52` and both filters in `scripts/check-leaks.mjs` (those need `CommandLine`, so add it to the list there). Update spec §3.4 wording.
2. **Windows now spawns PowerShell on every reaper call, including poll loops.** `reapDeadJobs` (`tracked-jobs.mjs:423-433`) runs the batch probe whenever a live job with identity exists, and it is called from `buildSingleJobSnapshot`/`buildStatusSnapshot` (`job-control.mjs:220/248/266/297`), `assertThreadIsFree` (`codex.mjs:1339`), `resolveLatestTrackedTaskThread` (`codex-companion.mjs:528`), the Stop hook (`stop-review-gate-hook.mjs:236`) and the `status --wait`/`--await` loops (`codex-companion.mjs:455-461`, 1–2 s interval). In v1.4.0 the win32 reaper cost nothing; now a five-minute `--await` launches `powershell.exe` ~300 times (0.3 s warm, up to 3 s cold each), and a probe that times out once trips the 60 s breaker for that process. The spec is silent; a user would not expect this. Fix (smallest): in the win32 batch branch only, memoise `{pid → identity, at}` per process with a short TTL (a few seconds) — kills never read it, the script re-verifies itself; or apply a probe-interval floor in the two poll loops. At minimum document the cost in README «Windows».
