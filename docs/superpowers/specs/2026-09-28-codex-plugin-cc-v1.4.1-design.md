## 1. Goal

On Windows the plugin refuses every kill that starts from a stored process record (`/codex:cancel`, `SessionEnd` cleanup of a still-running job, stale-broker replacement, broker teardown) with `identity-unavailable`, because `getProcessIdentity` returns `null` there. v1.4.1 gives Windows the posix guarantee: a recorded PID is signalled only once it is proven to still be the recorded process, and its tree goes with it. The fail-closed rule does not change: **an identity that cannot be read never authorises a destructive action, and an outcome that cannot be verified is never reported as delivered.**

Success:
- On windows-latest CI: `cancel` of a direct-transport background job (turn interrupt ignored by the fake) kills the worker and the `cmd.exe → node → fake codex` tree under it; cancelling a brokered job leaves the shared broker and its whole subtree alive and a new job still runs through that same broker afterwards; `SessionEnd` tears down the session's broker from its record when the broker accepted `broker/shutdown` but did not exit; a record whose identity no longer matches the live pid is never signalled; a root that died **before** `cancel` is failed by the reaper (nothing is signalled by number); survivors found **during** a kill make `cancel` answer `cancellationPending` with the survivors (pid + identity) reported and logged, never `cancelled`; a planted `powershell.exe`/`powershell.cmd` in the workspace or a relative `PATH` entry is never executed.
- posix behaviour unchanged except §6.
- README «Still limited until v1.4.1» removed; CHANGELOG 1.4.1; upstream comments for #743 (win32), #423/#577, #336, #416, #487, #718 and the retest asks.

Out of scope: lock-ticket identity on win32 (PID-liveness stays), lease files for `status`, darwin birth-time identity, `review --background` detachment (#615, v1.5.0), Job Objects (descendants spawned after the kill snapshot are best-effort, §5), Constrained Language Mode support (CLM → refuse, §5), and **persistent orphan tracking**: a survivor of a kill is reported with its identity and logged, but no record follows it across later commands — that would need every state writer (worker terminal write, index cap, cancel resolution, SessionEnd budget) to agree on a new field, which the plan reviews showed to be a release of its own (v1.4.2 if Windows users report leaked subtrees; §5).

## 2. Trust boundary and constraints

- **Windows directory.** `systemRoot(env)` takes `env.SystemRoot`/`env.SYSTEMROOT`, requires `^[A-Za-z]:\\[^\\/]+` and the existence of `<root>\System32\WindowsPowerShell\v1.0\powershell.exe`; otherwise the launcher is `unavailable` **and the breaker trips**. The plugin process's own environment is trusted (it was in v1.4.0 too; a project that can rewrite it via Claude Code settings is outside this model). The model covers repository *contents*: files, cwd, relative `PATH` entries, and everything a job's environment could inject into a child (`PSModulePath`, CLR profiler variables).
- **Clean child environment.** PowerShell gets exactly: `SystemRoot`, `windir` (= root), `TEMP`/`TMP` (from env if `path.win32.isAbsolute`, else `<root>\Temp`), `PATH=<root>\System32;<root>`, `PATHEXT=.EXE`, `PSModulePath=<root>\System32\WindowsPowerShell\v1.0\Modules`, `NoDefaultCurrentDirectoryInExePath=1`, plus two data-location pass-throughs taken from the parent env only when they are absolute paths: `LOCALAPPDATA` and `PSModuleAnalysisCachePath` (rev. 11: without them PowerShell 5.1 cannot find its module-analysis cache and re-analyses modules on every launch — 22–33 s per start on hosted Windows, measured; with them 0.3 s; neither variable selects an executable, autoload stays limited to the pinned `PSModulePath`). Nothing else. cwd = `<root>\System32`.
- **Launch.** Only that absolute path; `-NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <base64 UTF-16LE>`; `shell:false`, `windowsHide`. Scripts use cmdlets and .NET only; **no external program is started by any script** (the `taskkill.exe` fallback of rev. 2 is gone: a kill that the pinned handle cannot deliver is `kill-failed`, not a second try by number).
- **Output protocol.** Each script prints only lines matching `^[A-Z]+( \d+)*$`, checked on the exact text between line breaks (no trimming: a trailing space, TAB or NBSP, or an empty line, is junk; only the newline that ends the last line is optional). The rule applies to every PowerShell launch the project makes whose output feeds a decision, including the CI leak check and test helpers. One exception, by name: a launch made only to print a human-readable table for an operator (the CI leak check's diagnostic run after a leak was already counted) may print anything, because nothing reads it — probe: `ID <pid> <filetime>`; kill: `KILL` (the destructive phase has begun), then `OK`, or one `SURVIVOR <pid> <filetime>` line per node whose exit could not be confirmed (identity taken from the still-pinned object, before `Dispose()`). A result counts only when the whole expected sequence is present; a foreign line anywhere invalidates it (exit 0 with junk is *not* delivered). Once an exact `KILL` line was seen anywhere in the output, a corrupted answer still means «attempted, unverified». Nothing localised is parsed.
- **Budgets.** Every probe/kill has a caller-supplied finite `timeoutMs ≥ 1`; otherwise «no probe» → `identity-unavailable`. A kill needs `timeoutMs ≥ 750`; below that it is `identity-unavailable` without spawning. The kill script receives an **absolute** UTC deadline (JS clock at launch + `timeoutMs − 500`, as a FILETIME), so PowerShell start-up time is counted; every wait is bounded by the remaining budget and the destructive phase is skipped (→ 245) when less than 250 ms remain before it starts.
- **Exit 245 and breaker scope (rev. 12).** The kill script exits `245` (`WINDOWS_KILL_ABORTED_EXIT`) when it aborts before the destructive phase for a reason that says nothing about the launcher: budget shortfall (< 250 ms left) or a child that exists but cannot be pinned for a reason other than `ArgumentException`. `245` maps to `identity-unavailable` and does NOT trip the launcher breaker; `244` stays for Constrained Language Mode and does trip it. A kill that times out (`runPowerShell(..., { tripOnTimeout: false })`) does not trip the breaker either — the target was slow, not the launcher; a probe timeout still trips.
- **PID range.** Both scripts and their JS entry points accept only `1 ≤ pid ≤ 2147483647` (`Get-Process -Id` and `GetProcessById` take `Int32`); an out-of-range pid is `null`/`identity-unavailable` and never poisons a batch.

## 3. Design

### 3.1 Identity string

`win32:<FILETIME UTC>` = `Process.StartTime.ToFileTimeUtc()` read through a pinned process object (§3.4) — the kernel creation time (100 ns). Two reads of the same process agree; a process that inherited the PID never does. Legacy records (`pidIdentity: null`) keep refusing on win32.

### 3.2 Launcher

`runPowerShell(script, { timeoutMs, env, runCommandImpl, existsSyncImpl, now })` → `{ status, stdout, timedOut, unavailable }`. Breaker (`WINDOWS_IDENTITY_CIRCUIT_MS = 60 s`, monotonic `performance.now()`, injectable) trips on: invalid root, `ENOENT`, `ETIMEDOUT` (what `spawnSync` reports), exit 244. A success closes it. While open, callers get `unavailable` without spawning.

### 3.3 Probes

- `getProcessIdentities(pids, options)` → `Map<pid, string|null>`; **win32 only** batches: one PowerShell run over ≤ 256 deduplicated Int32 pids. The script starts with the same `LanguageMode` guard as the kill script (CLM → exit 244 → breaker); for each `Get-Process -Id … -ErrorAction SilentlyContinue` object it pins `$null = $p.Handle` and prints `ID <pid> <StartTime.ToFileTimeUtc()>` inside `try { } catch { }` — an unreadable start time (access denied, exited) prints nothing → `null`. Extra pids beyond 256 stay `null`. posix: loops the unchanged per-pid probe.
- `getProcessIdentity(pid)` on win32 = batch of one; own-pid cache; default `timeoutMs` 10000.
- `reapDeadJobs` batches **on win32 only**, and only for records that passed the terminal-file and liveness checks; the posix branch and its per-pid budget recalculation are untouched. Empty Map = unknown → job left alone.

### 3.4 Kill: `terminateRecordedProcess` on win32

Inputs: `pid`, recorded `identity`, `exclude: [{ pid, identity }]` (the workspace's recorded broker `pid` + `pidIdentity` from `loadBrokerSession`, when the caller kills a worker; a broker record without a `win32:` identity cannot be excluded safely, so on win32 the caller then refuses the kill with `identity-unavailable` instead of calling), `timeoutMs`. One PowerShell run:

0. **Guards.** `$ExecutionContext.SessionState.LanguageMode -ne 'FullLanguage'` → exit 244 (CLM cannot call `GetProcessById`/`Kill`; refusing beats a misleading 241). Deadline `= now + <timeoutMs − 500>`.
1. **Pin the root.** `$root = [System.Diagnostics.Process]::GetProcessById(pid)`; `[System.ArgumentException]` → 241 (the documented «not running» error); any other exception → 245 (rev. 12: not a launcher failure). Then `$null = $root.Handle` — in .NET Framework this opens `PROCESS_ALL_ACCESS` and **caches the handle on the object** until `Dispose()`, so every later `StartTime`/`Kill()`/`WaitForExit()` on `$root` acts on that pinned process object, and a PID recycled after this point cannot be reached through it. `.Handle` failing (access denied) → 245 (rev. 12). The whole script runs inside one `try/finally` that disposes every pinned object.
2. **Verify.** `$root.StartTime.ToFileTimeUtc().ToString() -ne '<recorded>'` → 242.
3. **Tree.** `Get-CimInstance -ClassName Win32_Process -Property ProcessId,ParentProcessId,CreationDate | Select-Object ProcessId, ParentProcessId, CreationDate` (rev. 12: `-Property` projection, `CommandLine` never computed for the kill). BFS from the root over `ParentProcessId` with a visited set. For each child row: `GetProcessById` throwing `ArgumentException` means the child is already gone → skipped (proven); **any other failure to pin it (access denied, CLM) aborts the preflight with 245 (rev. 12)** — a child that exists but cannot be verified must not silently drop out of the completion guarantee. An opened child is admitted only if (a) its pinned start time equals the row's `CreationDate` at microsecond precision, computed with exact `Int64` arithmetic (`$t - ($t % 10)` on UTC ticks — no floating point), (b) that value ≥ the parent's, (c) it is not an excluded process: exclusion is checked only AFTER the child is pinned and its start time read, and applies only when `exclude` names its pid AND the pinned start time equals the given identity (rev. 12; no bare-pid and no command-line-substring exclusion — a child that merely mentions `app-server-broker.mjs` in an argument is an ordinary child; an exclusion whose identity does not match is simply not an exclusion). The shared broker a worker may have started lazily is its child by `ParentProcessId` but has its own lifecycle; its whole subtree is left alone). (rev. 13) An admitted child that is not a verified `$exclude` entry gets ONE filtered `Get-CimInstance -Filter "ProcessId = <cid>" -Property CommandLine`; if the command line contains `app-server-broker.mjs` it is an unrecorded broker (TOCTOU between the presence read and this snapshot): it and its subtree are never enqueued or killed, it stays pinned, and after the destructive phase it is printed as `SURVIVOR <pid> <filetime>` with exit 243 even when everything else exited — cancel stays pending, SessionEnd keeps the record, and the next cancel finds the broker record and excludes it silently. A child failing (a)/(b) is a stranger holding a reused pid → skipped (proven not ours). If fewer than 250 ms remain before the deadline → 245. Prints `KILL` once the tree is fixed.
4. **Kill.** Children first (reverse BFS), `.Kill()` on each pinned object; a `Kill()` exception marks the node unconfirmed (it still goes through step 5, which decides).
5. **Verify exit.** For each node, `WaitForExit(min(250, remaining))` loops until the deadline; a node whose exit is confirmed is done; a node still alive, or one whose `WaitForExit`/`HasExited` threw, is a **survivor** (unknown ≠ exited). All confirmed → `OK` + exit 0. Otherwise one `SURVIVOR <pid> <filetime>` per survivor (the filetime read from the pinned object — proof of *which* process survived, so a later report can never be confused with a reused pid) + exit 243. Errors in this phase → 243 with the whole tree listed.
6. `Dispose()` every pinned object in `finally`.

JS mapping — the exit code classifies, the protocol lines refine, and any contradiction between them is an unknown outcome: `killStarted` = an exact `KILL` line appears anywhere in the raw stdout. Exit 0: exactly `KILL`,`OK` → `{ attempted: true, delivered: true, method: "handle", reason: "identity-match" }`; anything else → `kill-failed` + `unverified` when `killStarted`, else `identity-unavailable`. Exit 241 / 242 with no `KILL` line → `process-missing` / `identity-mismatch` (`attempted:false`); with a `KILL` line (impossible by construction, hence unknown) → `kill-failed` + `unverified`. Exit 243 → always `attempted:true`, `kill-failed`; `survivors: [{ pid, identity }]` filled only from a clean `KILL`,`SURVIVOR …`… sequence, otherwise `[]` + `unverified`. Exit 244, breaker, invalid identity, out-of-range pid, budget < 750 → `identity-unavailable` (no `KILL` can precede a 244; if one does → `kill-failed` + `unverified`). Timeout / any other status → `kill-failed` + `unverified` when `killStarted`, else `identity-unavailable`. Exit 245 = aborted before the destructive phase (budget/pin error) → `identity-unavailable` without tripping the breaker (rev. 12). posix branch and `terminateProcessTree` unchanged.

`delivered: true` means: the root and every admitted descendant were confirmed exited before the deadline. Descendants spawned after the snapshot are outside the guarantee (§5).

### 3.5 Capture at spawn

`spawnBrokerProcess` (`broker-lifecycle.mjs:282`), the background-worker spawn (`codex-companion.mjs:958`) and `runTrackedJob` (`tracked-jobs.mjs:183`) already call `getProcessIdentity`; once win32 returns a value they record it. Formats unchanged.

### 3.6 Sites, and the cancel contract

| Site | Today | v1.4.1 |
|---|---|---|
| `terminateRecordedProcess` win32 without identity | `identity-unavailable` | unchanged |
| `terminateRecordedProcess` win32 with identity | `identity-unavailable` | §3.4 |
| `getProcessIdentity` win32 | `null` | §3.3 |
| `ownsBrokerProcess` win32 | `true` (fallback only) | unchanged; teardown reaches the identity path |
| lock tickets | PID-liveness | unchanged |
| `cancel` win32 | `cancellationPending`, exit 1 | kills (§3.4 with `exclude = [{ pid: broker.pid, identity: broker.pidIdentity }]`; broker record without identity → refused `identity-unavailable`) |

- **Mismatch.** `resolveCancelableJob` runs the reaper first (`job-control.mjs:297`); a proven mismatch becomes `failed («pid reused»)` before cancel touches the pid, so cancel answers that the job is no longer active (exit ≠ 0) and the stranger is never signalled. The Windows E2E tampers the identity the reaper actually reads (the indexed record via `upsertJob`, mirrored into the job file).
- **Survivors (win32 only).** A kill that ends `kill-failed` reports its survivors (pid + identity from the pinned objects) and `cancel` answers `cancellationPending: true, reason: "kill-failed", survivors` (the field is present only when non-empty); the job stays `running` — never `cancelled` — while its root is alive or the outcome is `unverified`. The survivors are written to the job log (`worker tree survivors: <pid>:<identity> …`) and to stderr (with `--json`, stdout stays a single JSON document). Nothing persists them as records: once the root is gone the reaper fails the job as today, and a child that outlives its root is a documented leak with **no upper bound on its lifetime and no later cleanup attempt** — the identity in the report is diagnostics for the operator, not a record anything will kill later. README states this. On posix the cancel reasons and JSON stay exactly as in v1.4.0 (`survivors` never appears).

### 3.7 Budgets and records (win32 only)

- SessionEnd: worker kills `min(WIN32_KILL_STEP_MS = 4000, remaining/2)`; broker teardown `min(4000, remaining)`; the kill script's internal deadline is `timeoutMs − 500`, so a run never exceeds its step. What does not fit → `budget-exhausted`, left to the next SessionEnd or the idle timeout. Posix keeps `IDENTITY_PROBE_MS = 2000` and its halving.
- **Records on unknown outcome (SessionEnd only, win32 only).** The decision is made on the **whole-tree outcome**, not on the root alone: `kept: true` when the reason is `identity-unavailable`, timeout, or `kill-failed` (any survivors or `unverified`), regardless of whether the root itself is still alive; `kept: false` for `identity-match`+delivered, `process-missing`, `identity-mismatch` (proven not ours — the record is stale, not unknown) and `no-pid`. `teardownBrokerSession` only retains files when called with `keepOnUnknown: true`, which only the SessionEnd hook passes; `ensureBrokerSession`'s stale replacement calls it as today and keeps replacing the record (it must never block a user on a broken PowerShell). - **Worker cleanup in the hook (win32 only)** follows a narrower rule than the broker table above, and only for the *current* outcome: a job whose kill ended with survivors or `unverified` is kept and its survivors logged, even when its root is already dead; a refusal (`identity-unavailable`, `identity-mismatch`) keeps the job only while `isPidAlive(pid) !== false`, exactly as today; a dead root with no survivors reported is dropped. «Kept» here means kept from this hook's prune — the reaper that runs right after may already turn a dead-root job into `failed` in the same SessionEnd; nothing promises the job stays `running` until the next session.
- Test knob `CODEX_COMPANION_BROKER_HANG_ON_SHUTDOWN=1`: the broker acknowledges `broker/shutdown` but does not exit, so the SessionEnd kill path is exercised end-to-end.

## 5. Rollout and risks

- CLM/AppLocker: scripts exit 244 at the guard → `identity-unavailable`, records kept at SessionEnd, behaviour otherwise equals v1.4.0; README says so. No CLM E2E (needs a lockdown policy the runner does not have); the guard is unit-tested by script text.
- PowerShell 5.1 missing or root invalid: breaker, v1.4.0 behaviour.
- No Job Object: a descendant spawned after the snapshot survives the kill; like a survivor that outlives its root, it has no lifetime bound and no later cleanup attempt from the plugin (it belongs to nobody the plugin records); documented in README.
- No orphan tracking: a survivor reported by a kill is logged with its identity but not followed by any record; if Windows users report leaked subtrees, v1.4.2 adds a per-job `orphans` record with a single owner of its lifecycle (the plan reviews of this release enumerate the writers it must reconcile).
- A process the plugin may not open (`.Handle` access denied) is `identity-unavailable`, never killed by number.
- Upstream comments only after the user approves; the «verify» bucket gets retest asks.

## 6. posix changes (the only ones)

1. `processCommandLine` ps branch refuses a budget `≤ 0` (was: spawned `ps` with a 1 ms clamp).
2. `teardownBrokerSession` gains a `kept` field in its result (always `false` on posix); existing tests that `deepEqual` the result are updated.
3. `cancel`'s pending reason/JSON on posix is byte-identical to v1.4.0 (`not-delivered` etc.); the `kill-failed`/`survivors` shape, the broker-pid lookup for `excludePids`, and the `CODEX_COMPANION_BROKER_HANG_ON_SHUTDOWN` test knob are win32-only.
4. The posix `Broker teardown:` stderr line gains a `kept=` field (diagnostic only, always `false` on posix).
Everything else — reaper loop, hook budgets, broker teardown timing, poll intervals, stale replacement — is unchanged on posix; every new behaviour sits behind `platform === "win32"`.
