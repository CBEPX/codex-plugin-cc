# Windows

## Spawn path (v1.4.0)

As of v1.4.0, the plugin no longer spawns commands through `$SHELL` on Windows (usually Git Bash, which mangled `taskkill` and other arguments): `codex`, `npm` and `git` are resolved by a file-based lookup over the absolute `PATH` entries × `PATHEXT` (relative `PATH` entries and the current directory are skipped; `where.exe` is not used), `.exe` files run directly and `.cmd` shims run through `cmd.exe`. This is the spawn path behind the commands, `/codex:review`, `/codex:adversarial-review` and background `task`/`--await` jobs. Separately, the `Stop`, `SessionStart` and `SessionEnd` hooks now read stdin with a bounded deadline instead of a blocking read, so a disabled review gate no longer hangs until the hook timeout on Windows. `/codex:transfer`'s own Windows-specific issues (verbatim `\\?\` paths, ledger lookups) are unrelated to these changes and are not fixed.

## Verified kills from stored records (v1.4.1)

As of v1.4.1, kills issued from stored process records — `/codex:cancel`, `SessionEnd` cleanup of a still-running job, stale-broker replacement, and broker teardown — work on Windows. The plugin captures a process identity (start time) for workers and the broker at spawn and verifies the recorded pid against it before killing; the verified process tree is then terminated children-first through one in-box Windows PowerShell 5.1 run with pinned handles (no `taskkill`). A pid that is provably gone is reported as `process-missing`; the kill then looks for orphans it left (its descendants still linked to it by parent pid, each started no earlier than its parent; the shared broker, excluded by its verified identity, is never one) and reports them without killing them. A descendant whose intermediate parent also exited before the kill is no longer linked to the root and is not found (known limitation). `/codex:cancel` marks such a job cancelled only when there are none and the worker itself recorded a closed exit (its final record marked as written after its app-server client closed: `job.workerClosed`, a boolean shown by `status --json` / `result --json`, present and `true` only on a terminal record the worker itself wrote after its app-server client closed, and absent on records written by the crash guard, the reaper or `/codex:cancel` and on every pre-1.4.1 record; a vanished worker without it, a crash-guard failure or a v1.4.0 record leaves the cancel `cancellationPending` for the reaper), and answers `cancellationPending` with the orphans as `survivors` otherwise; a background worker's pid is recorded before its identity is probed, and a worker whose job was cancelled before it started does not run it; other kills clean the record up. `status` and the reaper probe all live jobs in one PowerShell run. If part of the tree outlives the kill, `/codex:cancel` reports `cancellationPending` with the `survivors` (pid and identity) and never marks such a job cancelled; if the outcome of a kill cannot be verified (refused, unverified or timed out), `SessionEnd` keeps the record of that job or broker (`kept=true` in the teardown line, survivors included) and re-judges it at the next `SessionEnd`. When the root itself died but part of its tree survived, the reaper fails the job during the same `SessionEnd` (or the next `status`), so the survivor is only reported and logged, not re-judged. If another process (the worker or the reaper) already finished the job record before `/codex:cancel` writes, the record is kept and its status reported — unless the cancel's own interrupt was acknowledged or its kill delivered, in which case the worker's record becomes `cancelled` as in v1.4.0; a failure the reaper recorded (the worker exited before completing) is always kept. A broker writes its record (first without a pid, then with pid and identity) under the state lock before and around its spawn, and a Windows `/codex:cancel` holds that lock from reading the broker record through the kill, so no broker can start unseen in between; `status` and other commands may wait up to a few seconds for that lock. Two broker starts that race are settled inside that lock: the later one waits for the earlier one's broker instead of spawning another. A broker start that fails is killed through the same verified kill, and its record and files are removed only once the process has exited (it is given up to 2 s); otherwise both are kept, with its identity. `SessionEnd` keeps the record and files of a broker that is still starting (`reason=starting kept=true`). A broker whose record is missing or unreadable while its endpoint is still advertised is presumed present, so kills that would need to exclude it are refused (`identity-unavailable`). The shared broker is excluded from a worker's kill tree only by a verified identity, so it is never killed together with a worker (a broker record without an identity refuses the worker kill). A `/codex:cancel` issued during the first seconds of a task, while the shared broker is still starting, can therefore come back `cancellationPending` (`identity-unavailable`); re-run the cancel once the broker record carries its identity. A newly started broker whose identity cannot be read yet is not used: requests go through the direct transport until its identity is recorded, and the broker is then shared as usual.

## Limits

Limits: descendants spawned after the tree snapshot are outside the guarantee. On every platform, a brokered `/codex:cancel` confirms the worker, not the turn: it sends `turn/interrupt` and kills the verified worker, and reports `cancelled` once the kill is delivered or the interrupt acknowledged, even if the app-server behind the shared broker ignores the interrupt and keeps running that turn; the job record says `cancelled` while the turn may keep using the broker until it finishes on its own or the broker is shut down (`SessionEnd`, idle timeout); planned for v1.4.2: wait for the turn's own terminal notification (`turn/completed` with status interrupted) before reporting `cancelled`. `workerClosed` proves that the app-server client closed, not that every descendant exited: on the direct transport `close()` resolves when the app-server child exited or when the 5 s close deadline passed, so on Windows a job whose root vanished (`process-missing`, exit 241) and whose orphan walk found nothing can be marked `cancelled` on the strength of that marker while a grandchild under an already dead intermediate parent is still running (the walk cannot see it, as described above); planned for v1.4.2: such a direct job stays `cancellationPending` unless the app-server's exit was observed. A survivor process that outlived its root is not tracked and is never retried by pid: it is a known leak with no upper bound, and its pid and identity in the cancel output and the log are diagnostics for the operator. Under PowerShell Constrained Language Mode or AppLocker the identity cannot be read, so kills from records are refused (`identity-unavailable`): `SessionEnd` keeps the broker and job records, while `/codex:cancel` sends the turn interrupt and leaves the job running with its record in place. The shared broker is still spawned, but requests use the direct transport until its identity can be read, which under these policies is never. An argument containing CR/LF is refused with an error, and `%VAR:a=b%` substitution inside a `.cmd` shim argument remains a documented limitation (see the comment block in `plugins/codex/scripts/lib/process.mjs` near `resolveExecutable`/`buildLaunch`).

## Requirements

Requirements: `cmd.exe` (for `.cmd` shims) and Windows PowerShell 5.1 (for the v1.4.1 kills) ship with Windows, so nothing extra needs installing, and a Store `pwsh` is not needed. `codex` and `npm` must be on the Windows `PATH` as `.cmd`/`.exe` (a global `npm install -g @openai/codex` already does that for `codex`); a `codex` or `npm` that only exists inside Git Bash (an alias, a shell function or a bash-only `PATH` entry) is no longer found. On Windows a long-running `task --await` or `status --wait` loop probes the live jobs with at most one PowerShell run per 2 s (the probe result is remembered inside that process; a standalone `/codex:status` still runs one probe).

## State directory fallback

When `CLAUDE_PLUGIN_DATA` is not set, job state falls back to a per-user directory: `%LOCALAPPDATA%\codex-companion` on Windows as of v1.4.0 (a private `codex-companion-<uid>` directory under the system temp directory elsewhere). If a pre-1.4.0 state root under `%TEMP%\codex-companion-user` already exists, it keeps being used (with a one-line notice) until you remove it; nothing is migrated. On Windows, `state.json` reads and writes and lock-ticket reads also retry briefly (up to 20 attempts, roughly 300 ms worst case) on `EPERM`/`EBUSY`/`EACCES` when another process holds `state.json` or a lock ticket open.
